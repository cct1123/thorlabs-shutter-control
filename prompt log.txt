## Goals

* reduce file count where sensible;
* reduce unnecessary classes, wrappers, factories, registries, adapters, managers, services, and helper layers;
* merge modules that exist only to preserve artificial separation;

* simplify test fixtures and mocking infrastructure where lighter tests provide equivalent confidence;
* preserve important boundaries around hardware, external APIs, safety, persistence, or other genuinely unstable interfaces.

## Decision Rule

For every abstraction, file, module, configuration option, and dependency, ask:

> Does this materially improve correctness, testability, safety, readability, reuse, or isolation of a genuinely unstable boundary?

If not, remove or collapse it.

Prefer:

**direct code > framework machinery**
**small module > layered hierarchy**
**explicit call > generic dispatch**
**plain function > manager/service object**
**one clear implementation > extensibility scaffold**
**local configuration > configuration framework**
**simple test double > elaborate mocking framework**

## Preserve

Do not simplify away:

* required functionality;
* public APIs that are actively used;
* meaningful hardware/device boundaries;
* safety checks;
* error handling that protects correctness;
* tests covering important behavior or regressions;
* reproducibility;
* packaging required for actual use;
* interfaces that isolate unstable vendor or external dependencies;
* documentation needed by users.

## Avoid

Do not:

* rewrite the whole project merely for stylistic consistency;
* introduce a new framework during cleanup;
* replace simple working code with clever abstractions;
* create new generic infrastructure to remove old generic infrastructure;
* optimize for hypothetical future requirements;
* preserve scaffolding only because it might someday be useful.

## Cleanup Process

1. Inspect the full repository and identify the actual required behavior.
2. Map the current architecture and dependency flow.
3. Identify obvious dead code and redundant files.
4. Identify unnecessary abstraction layers and indirection.
5. Propose the simplest architecture that preserves current requirements.
6. Simplify incrementally.
7. After each meaningful reduction, run the relevant tests.
8. Remove tests, fixtures, and configuration that became obsolete.
9. Run the complete test suite, linting, type checks, and build/package checks that are relevant.

* fewer concepts;
* fewer files;
* fewer dependencies;
* fewer hidden control paths;
* fewer configuration options;
* less boilerplate;

* one-line wrappers;

* unused extension points;

* USB;
* initialization ordering;
* polling/state refresh;
* timing;
* shutter configuration;
* interlock state;
* controller configuration;
* backend implementation;
* controller abstraction;
* GUI state management.

Prefer root-cause correction over special-case workarounds.

---

# 13. Preserve Software Regression Coverage

After every implementation change caused by hardware findings:

1. rerun relevant automated tests;
2. add or modify tests to capture the newly discovered behavior where appropriate;
3. ensure simulated behavior still represents the application contract;
4. rerun the full software test suite before declaring the change complete.

Hardware fixes must not silently regress previously working software behavior.

---

# 14. Update Persistent Engineering State

Maintain `STATE.md` throughout the hardware phase.

Record concise current engineering state, including:

* actual hardware configuration;
* validated functionality;
* hardware tests passed;
* hardware tests failed;
* observed discrepancies;
* current diagnoses;
* implementation changes;
* remaining requirements;
* next engineering priority.

Use durable engineering records for important physical observations, test results, and design decisions.

Do not turn `STATE.md` into a chronological log.

---

# 15. Engineering Evidence

Create durable evidence records for important hardware findings.

For example:

* physical open/close verified;
* device reports state X after command Y;
* reconnect succeeds after USB restoration;
* safe shutdown closes shutter;
* physical state cannot be independently queried;
* actual API behavior differs from documentation.

Record enough information to reproduce or understand the test:

* hardware configuration;
* command/action;
* software result;
* physical result;
* pass/fail;
* implication.

---

# 16. Human Interaction During This Phase

Minimize human intervention.

If the agent can directly interact with authorized hardware, proceed within the approved validation plan and project constraints.

If human physical observation or intervention is required, ask for the **smallest specific action or observation needed**.

Examples:

Good:

> Confirm whether the shutter physically opened after the command and report only `open`, `closed`, or `no motion`.

> Disconnect the KSC101 USB cable, wait five seconds, reconnect it, and tell me when Windows detects the controller again.

Avoid:

> Check the hardware.

Do not ask the human to choose routine software/debugging actions.

---

# 17. Scope Discipline

The goal of this phase is physical validation and correction of the existing system.

Do not expand scope by adding unrelated features such as:

* experiment scheduling;
* remote control infrastructure;
* databases;
* authentication;
* complex GUI redesign;
* generalized device frameworks;
* support for unrelated Thorlabs products;

unless required to satisfy an existing project requirement.

Keep the KSC101 controller simple and reliable.

---

# 18. Acceptance Criteria

The physical validation phase is complete when the project demonstrates, on the actual hardware:

1. reliable discovery/connection;
2. correct controller identification;
3. controlled physical shutter opening;
4. controlled physical shutter closing;
5. repeatable open/close operation;
6. correct state/status behavior to the extent supported by the device;
7. clean disconnect/reconnect behavior;
8. useful error handling;
9. validated shutdown behavior;
10. correct operation through the Python controller API;
11. correct operation through the Plotly Dash GUI;
12. successful software regression tests after hardware integration;
13. documented actual hardware configuration and remaining limitations.

A command returning successfully is not sufficient evidence of physical actuation.

Physical behavior must be observed or otherwise independently validated.

---

# 19. Completion State

When all required physical acceptance criteria pass:

transition the project state to:

`HARDWARE_VALIDATION → VALIDATED`

Then:

* update `STATE.md`;
* record final hardware evidence;
* update documentation with the actual supported configuration;
* ensure installation/run instructions are correct;
* rerun the full automated test suite;
* perform final controller and GUI smoke tests;
* update the final engineering report.

The final report should clearly distinguish:

* software-tested behavior;
* physically validated behavior;
* inferred behavior;
* known device/API limitations.

---

# 20. If Validation Cannot Be Completed

If a real external blocker prevents completion, do not keep searching or modifying software without evidence.

Record:

* exact blocker;
* completed hardware validation;
* remaining unvalidated requirements;
* why further autonomous progress is not useful;
* exact action needed to resume.

Then stop in a clearly documented blocked hardware-validation state.

---

# Final Engineering Loop

During this phase, operate autonomously according to:

**Inspect actual hardware
→ Validate assumption
→ Observe behavior
→ Identify discrepancy/gap
→ Diagnose
→ Implement focused correction
→ Run software regression tests
→ Retest physical hardware
→ Update persistent state
→ Check requirements
→ Repeat**

Continue until the system reaches either:

**VALIDATED**

or

a genuine external blocker that prevents further useful engineering progress.

Do not stop merely because the physical device behaves differently from the software assumptions. Treat discrepancies as engineering evidence and continue the diagnose–fix–retest loop.
