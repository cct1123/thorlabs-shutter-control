01 · System and evidence boundaries

The tested configuration was Windows → USB → KEH3 left bay → KSC101 → SH05R. The cube reported firmware 1.0.7, hardware revision 3; the environment was Kinesis 1.14.60.27990, Python 3.12.7 x64 and pythonnet 3.1. The FTDI/Kinesis USB interface had no assigned COM port. Discover the cube identity through the vendor SDK rather than selecting a serial COM port.S1 S5

03 · Correct interpretation of status and commands

Auto is a valid mode. Undefined operating-state value 0 is not evidence of Inactive. A clear SDK interlock bit means unknown in the observed contract, not “physical interlock disabled.” The key-related 0x2000 indication is separate. The four-state jack/key experiment did not establish a software-readable jack continuity signal.S1 S5 S6

Explicit operator confirmation records normal physical interlock/protection for a particular object and selected serial. It is evidence, not an SDK interlock write or bypass. This optional metadata does not gate commands. Users manage the physical interlock externally; identity, key and communication checks remain. Retargeting clears the confirmation; it does not transfer to a new object/process.S7

  • Connect: discover/select, initialize communication/polling and verify identity/feedback without explicit output or mode writes.
  • Open: current API sends Active only. Explicitly Disarm and read the Inactive/Manual baseline before enabling the channel. Read operation feedback separately. Active follows the selected mode.
  • Close: current API sends Inactive only and preserves mode. Use explicit Disarm for Inactive/Manual, then read feedback separately.
  • Cleanup: after a verified connection, attempt Close and release. A failed/unverified connection gets passive release; do not write output to an unverified identity.
  • Ownership: one process/operator owns a cube. Failed release retains the handle/claim; do not create a competing owner.

The hub attempts cleanup for every slot and aggregates failures. Calls are sequential: a native SDK hang can prevent later attempts, so a per-feedback timeout is not a total shutdown deadline.S6 S7

04 · TTL: useful partial results and a preserved failure

The user reported both IO1/TRIG1 and IO2/TRIG2 connected to nothing. The autonomous single-pair test covered disabled/output settings, input polarity, priming, Disarm, settings restoration and release. Original settings were TRIG1 input/high and TRIG2 output/high; these were restored afterward.S2

Both low cases reported status bits 8192. A separate Manual Open → 1-second added hold → Close positive control passed electronic feedback: 8193 → 8192. Every run ended Closed/Inactive/Manual with restoration/release. The initial IO1 mismatch was checked with a bounded 1-second read window; IO2 was tested independently. Arm was not repeatedly replayed to force an outcome.

Cause remains unknown. The observations do not establish a hardware defect, firmware defect, polarity defect or feedback defect. No driver workaround was added. External pulses, output voltage, independent blade observation and calibrated TTL timing remain untested. Preserve the documented precaution that active-low Arm may open immediately, even with an unplugged input.S2 S5

05 · Actual user experience, scale and focused fixes

The production GUI was exercised through real browser actions and actual USB feedback: manual Open/Close, refresh without replay, reconnect, passive TTL Read, global cleanup and normal Ctrl+C exit. A later GUI run recorded a 2.015-second visible added hold; that is host/browser behavior, not calibrated exposure. The controller readback and user-confirmed earlier sequence are distinct evidence.S1 S6

Manual controls, readiness hints and faults derive from the same status snapshots. Trigger settings are collapsible; edits stay as drafts until Apply, Read replaces drafts, Arm uses device settings, and refresh does not replay action clicks. Browser closure alone does not shut down the hardware owner.S7

Beyond three shutters

SLOTS = N in config.py / ShutterHub(slots=N) accepts a positive panel count. The default remains at least three and expands to fit supplied serials. Six/nine-device software lifecycles and empty three/six-panel browser layouts were tested. There is no application-defined count cap, but power, USB, host resources and sequential SDK latency still limit practical size.S4 S7

KEH6 USB compatibility is expected, not physically qualified. Per-cube addressing motivates that expectation; no KEH6 or multiple-pair bench PASS is claimed. KEH6 Ethernet mappings are not inferred. Full status reads include a polling wait: at default 250 ms per connected panel, six panels contribute at least 1.5 seconds of waits plus SDK time. Control is not simultaneous or synchronized.S4 S7 S8

Always choose the intended controller

Every hub GUI panel, including a single-panel session, requires a selected serial for Connect. Discover may visibly select a sole discovered device; verify it is the intended target before connecting. The direct create_app(KCubeShutter(...)) convenience API retains the driver’s optional-serial behavior.S4 S6

06 · A simpler procedure for the next session

  1. Connect/read: discover once, select the intended serial, connect and verify identity/communication. Stop on mismatch or failed reads. Status-only work ends with passive release and requires no motion.
  2. One functional cycle: with applicable authority/protection and current readiness, read status, Disarm and verify Closed/Inactive/Manual before explicitly enabling as needed; Open and verify; hold for the approved interval; Close and verify. Record whether the blade was independently observed.
  3. GUI/finish: check refresh without action replay, release/reconnect and expected readiness. Reuse the functional cycle if it ran in the GUI. Finish with Close & disconnect all and normal Ctrl+C; verify release/server exit.
Unchanged qualified USB bench: connect/read → Closed baseline → intended operation → Close/release. No repeated full commissioning, arbitrary cycle count, complete old bench form or approval between ordinary commands. Reuse established authorization within its scope; recheck transient/changed conditions.S5

Record only reproducibility-critical facts: date/purpose, code revision, actual selected mapping in secure local configuration, transport/changed settings, action/added hold, expected versus observed feedback, independent observation, errors and release outcome. Installation/firmware, Ethernet, electrical TTL, fault injection and physical timing are separate change-driven investigations.

For passive Ethernet qualification, first release competing owners and use the documented LAN-only arrangement. KEH3 uses one IP: hub 40303, left/middle/right bays 40304/40305/40306 and USB OUT 40307; USB IN must be disconnected for Ethernet operation. A matching cube identity/readback and passive release are the acceptance check. Historical hub-only discovery does not prove firmware incompatibility or current cube connectivity.S8

07 · Copyable starting points

Start a one-panel GUI

uv sync --locked
uv run --locked shutter-control

Close Kinesis and any competing controller program first. Open http://127.0.0.1:8050/, click Discover, check the serial, then Connect. Startup is passive; it does not open the shutter. This project uses Windows and the installed Kinesis runtime for hardware communication.

Prepare manual operation

Set SLOTS = 1 and optionally SERIAL_NUMBERS in src/thorlabs_shutter_control/config.py before launch. Users manage the physical interlock and source protection externally. There is no software interlock gate or confirmation flag. Verify the target, read status, establish Close, then perform the intended Open/approved hold/Close cycle. Keep Close and the independent bench shutdown action available.

Read status from Python without moving the shutter

from thorlabs_shutter_control import KCubeShutter, config

cube = KCubeShutter(config.SERIAL_NUMBERS[0])  # Set the actual selected identity locally.
try:
    print(cube.connect())
    print(cube.identify_device())
    print(cube.get_status())
finally:
    cube.disconnect(close_shutter=False)

This example releases communication only; it leaves output and mode unchanged. For an authorized operating session, use Close and normal shutdown after a verified connection. If connection identity fails, keep cleanup passive.

Add panels when needed

# In config.py: SLOTS = 6
uv run --locked shutter-control

This configures six GUI panels; it is not a six-device hardware qualification. Select each distinct target explicitly. Allow for sequential status/cleanup time and manufacturer power/USB limits.

Practical priority: use the demonstrated USB path for ordinary single-shutter work; choose additional tests only when their capability is needed. If TTL integration is next, resolve its preserved failure first. If LAN control is next, do the passive post-update bay test first. Physical timing and multi-pair work need their own evidence; no broad completion claim is justified.S1 S2 S5 S8

Quick self-check before a new task
  • Do I need only the demonstrated single-pair USB operation?
  • Does this task actually need TTL, LAN or multiple shutters?
  • Is functional blade observation sufficient, or does the experiment require independently measured timing?
  • What changed since the last successful run, and which check would reveal a problem?
